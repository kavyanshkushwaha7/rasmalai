## Spectator Mode disabled for launch — 2026-11-13

- **Severity addressed:** High privacy exposure through an active spectator path while the feature is intentionally unavailable for public launch.
- **Launch control:** `SPECTATOR_MODE_ENABLED` is server-only and defaults to disabled. The web route/page and realtime service use the shared strict-true parser. Locally, realtime explicitly takes the setting from `apps/web/.env.local` so an earlier shell or realtime `.env` value cannot silently disagree. Deployment must set the same false value in both server environments.
- **Realtime enforcement:** All spectator-only list, join, invitation, revoke, chat, and reaction events fail before membership queries or shared spectator quotas. Room broadcasts omit the spectator channel; an already-connected watcher is removed and receives the safe disabled event on the next heartbeat or room broadcast. Normal player authorization and channels remain separate.
- **Direct-route and Data API controls:** The watch page returns a safe “Spectator Mode is coming soon” screen before spectator queries. Migration `0012_disable_spectator_client_reads` replaces spectator-aware read predicates for room/game/match data with player-only predicates and revokes authenticated/anonymous/public direct `SELECT` on spectator invitations and spectator chat tables. It preserves records and server-only SECURITY DEFINER spectator RPCs.
- **Migration status:** Both configured runtime Transaction Pooler and admin Session Pooler identities match the local Supabase project reference. Migration `0012` was pending, then applied once via the migration-only URL. Read-only status is current at 12 migrations. No production project was contacted and no rows were modified.
- **Live permission evidence:** A verified-TLS read-only check over the restricted `prisma` runtime connection confirmed no authenticated direct grants for spectator tables/helper functions, retained server watch-RPC access for `prisma`, enabled game-state RLS, a player-only game-state policy, and zero visible game-state/move/match/roster rows for a synthetic nonmember identity. This is metadata/RLS evidence, not a user-to-user feature test.
- **Automated coverage:** Realtime tests cover default-off parsing, disabled spectator event rejection without database/quota calls, connected-socket eviction, and continued two-player chat. PGlite applies migration `0012` with the history and checks spectator direct-read denial while retaining server RPC behavior. Spectator Mode itself is **NOT TESTED as a feature** and must not be marked passed.
- **Re-enable path:** Preserve spectator code, data, RPCs, and migration. Re-enable only by setting the server-only flag to true on both services and performing fresh public/private invitation, revoked-access, RLS, live-board, and separate-chat authorization tests with authorized accounts.

## Phase 6 social-rate-limit blocker remediation — 2026-11-13

- **Severity:** High / public-launch blocker until end-to-end account-level quota behavior is verified; `0011` is applied to the test project.
- **Finding:** Under migrations through `0010`, database insert triggers counted only successful friend requests, message requests, and direct messages. Invalid/duplicate attempts that created no row did not consume those quotas. Request decisions, cancellation, unfriending, conversation open/read, and notification-read actions lacked shared quotas.
- **Code correction:** Social Server Actions now authenticate first, then commit an atomic PostgreSQL quota through `withRealtimeUser` before parsing mutation input or invoking the business RPC. That wrapper revalidates the Supabase access token with Auth and sets only the verified `auth.uid()` claim. Invalid input, self-directed requests, duplicates, missing objects, and unauthorized business attempts consume only the caller's quota. The app fails closed if the quota service is unavailable and uses a safe `rate-limit` feedback code.
- **No duplicate send count:** Friend requests, message requests, and direct messages reuse their existing shared 5/min, 5/min, and 30/min buckets. Migration `0011` detaches the old insert triggers for those three operations; the application preflight is now the sole charging point, so a successful send increments its bucket once. Other mutations use independent shared buckets: 30/min for friend decisions/cancel/unfriend; 30/min for message-request accept/reject; 60/min for conversation open; and 120/min each for conversation reads and notification reads.
- **Database boundary:** `0011` allows only the listed social action keys in a `SECURITY DEFINER` wrapper that accepts no user ID and is executable only by `prisma`. It revokes execute on social mutation RPCs from `PUBLIC`, `anon`, and `authenticated`, granting those operations to the server runtime role. Existing RLS policies and private read boundaries are unchanged. Direct browser PostgREST mutation calls are denied after the migration.
- **Migration and rollback:** `0011_social_action_rate_limits/migration.sql` changes no user, message, notification, match, or profile rows. It extends the rate-key constraint, updates the atomic policy, tightens RPC grants, and drops three triggers to prevent duplicate counting. `rollback.sql` restores the previous grants and triggers and drops the server-only wrapper; it deletes no user or rate-limit rows. Roll back the web app before executing the SQL rollback. The additive action keys/policy remain available so existing bucket data is preserved.
- **Local evidence:** PGlite applies migrations `0001`–`0011` in an ephemeral database. Tests cover concurrent caps, reconnect-equivalent calls, independent users, invalid self and duplicate requests with no extra row, notification-read attempts that update no row, cross-account message denial, all social RPC execute grants, successful inserts charged exactly once, and rollback behavior. The web tests verify authenticated → quota → validation/business-call ordering for every social mutation and safe error feedback.
- **Live boundary:** Before applying, a read-only `prisma migrate status` reported `0011_social_action_rate_limits` pending; migration `0011` was then applied to the configured test project only. A read-only follow-up reports schema up to date. Using the restricted runtime connection, an additional read-only check found all 11 social mutation/limiter functions executable by `prisma`, denied to `authenticated` and `anon`, quota table reads denied, and old send triggers absent. No production connection or user-data mutation was made. Live account-level social attempts remain untested.
- **HTTP response behavior:** There are no social REST API routes in this app; mutations use Next.js Server Actions and form navigation, so throttling returns the existing safe rate-limit page feedback rather than a standalone HTTP 429 endpoint. Any future REST endpoint must translate the shared denial to HTTP 429 and include a bounded retry policy.

## Findings and corrections

### 1. Migration credentials in the web environment

- **Severity:** High (configuration risk if the former setup instructions were followed).
- **Affected:** `.env.example`, `packages/database/.env.example`, `packages/database/prisma.config.ts`, `README.md`.
- **Why it mattered:** The admin `DIRECT_URL` could be copied into the web server environment, widening the impact of a web-server compromise.
- **Correction:** Root `.env.example` now contains only web runtime settings. `DIRECT_URL` is in a separate database migration example and must include verified SSL parameters. The web runtime does not read it.
- **Status:** Fixed in source and documentation. Local templates were checked without printing values.
- **Paid service required:** No.

### 2. PostgreSQL TLS verification

- **Severity:** Medium.
- **Affected:** `packages/database/src/index.ts`, `packages/database/prisma.config.ts`, `.env.example`, `packages/database/.env.example`.
- **Why it mattered:** The prior Prisma adapter did not configure a CA or require verified TLS.
- **Correction:** Runtime `DATABASE_URL` and migration-only `DIRECT_URL` require `sslmode=verify-full` and `sslrootcert`. Runtime Prisma reads the configured CA file and sets `ssl.ca` with `rejectUnauthorized: true`; Prisma migration config resolves the same project-root-relative path and rejects a missing certificate. Runtime SSL URL parameters are removed only after loading the CA, avoiding node-postgres replacing the verified TLS options.
- **Status:** Code/config checks and a read-only verified-TLS connection to the configured test project passed.
- **Paid service required:** No; use the project CA certificate.

### 3. Prisma identity accepted from an arbitrary UUID

- **Severity:** Medium.
- **Affected:** `packages/database/src/index.ts`, `packages/database/src/supabase-auth.ts`, all `withAuthenticatedUser` call sites.
- **Why it mattered:** A UUID alone is not proof of authentication. The old helper accepted any valid-looking UUID before setting RLS claims.
- **Correction:** The helper now accepts an access token and resolves its user ID through `GET /auth/v1/user` before opening a transaction. It still uses `SET LOCAL ROLE authenticated` and transaction-local claims so RLS applies. Current web call sites pass the session token from a `getUser()`-verified session. Tests reject a raw UUID as identity.
- **Residual limitation:** This direct-Postgres design synthesizes the claim after Auth verification. A holder of `DATABASE_URL` can still forge claims at PostgreSQL level; the runtime credential must remain server-only. RLS does not defend against a compromised database credential or arbitrary server code.
- **Paid service required:** No.

### 4. Profile privacy model

- **Severity:** Medium.
- **Affected:** `packages/database/prisma/migrations/0003_phase1_security_hardening/migration.sql`, `packages/database/prisma/schema.prisma`.
- **Why it mattered:** Table-level public reads also exposed timestamps, beyond the requested public game identity and stats.
- **Correction:** Migration `0003` grants column-level reads for `id`, username, nickname, avatar fields, games played, and wins only. Email and phone remain in Supabase Auth, not the public profile table. Public avatar viewing is preserved by the public bucket; the unnecessary object `SELECT` policy is dropped to avoid listing objects through that policy. The current schema has no `losses` column. [Supabase documents that public buckets serve objects without a SELECT policy](https://supabase.com/docs/guides/storage/buckets/fundamentals).
- **Status:** Applied in migration `0003`; live profile grant behavior was not re-tested in this task.
- **Paid service required:** No.

### 5. User-editable profile writes could change server-owned fields

- **Severity:** High.
- **Affected:** `packages/database/prisma/migrations/0003_phase1_security_hardening/migration.sql`, `packages/database/prisma/schema.prisma`, `apps/web/app/actions/auth.ts`.
- **Why it mattered:** Table-level authenticated updates let a user modify their own wins, games played, and timestamps through the Data API, bypassing web form validation.
- **Correction:** Migration `0003` revokes direct authenticated table writes, drops the owner insert/update policies, and exposes a `save_profile` security-definer function that derives the row ID from `auth.uid()` and accepts only validated username, nickname, and an owned avatar path. A database trigger manages `updated_at`; statistics and timestamps are not writable through the profile function. Public profile reads omit timestamps.
- **Status:** Applied in migration `0003`; Phase 2 functions preserve the restriction against direct profile writes.
- **Paid service required:** No.

### 6. Social and private-message access

- **Severity:** High because incorrect access could expose private conversations.
- **Affected:** `packages/database/prisma/migrations/0004_phase2_message_request_notifications/migration.sql`, `packages/database/prisma/migrations/0005_phase2_social_messaging/migration.sql`, `apps/web/app/actions/social.ts`, `apps/web/lib/social-data.ts`.
- **Why it matters:** Friends, message requests, conversations, messages, and notifications contain relationship and private communication data.
- **Correction:** Social tables grant only column-limited `SELECT` to `authenticated`; RLS limits requests to participants, conversations/messages/members to current conversation members, and notifications to their recipient. No direct social `INSERT`, `UPDATE`, or `DELETE` grants are given. Mutations use fixed `SECURITY DEFINER` functions with `search_path=pg_catalog`, derive the actor from `auth.uid()`, validate both sides of each request, enforce friend or accepted-request membership before sending messages, and create notifications in the same transaction. Conversation member `last_read_at` is not selectable by the peer. Direct conversations have a unique pair key.
- **Verification:** PGlite PostgreSQL tests apply migrations `0001`–`0005`, exercise friend request accept/reject paths, message request acceptance, one-to-one messaging, unread counts/read state, direct-write denial, and a third-user isolation case. Live Supabase metadata verified migration records, RLS/policy counts, function grants, runtime role switching, and lack of direct message writes. Actual user A/user B live app behavior remains untested.
- **Residual limitation:** There is no user-facing block/report control. Database block checks deny messaging if a trusted path has inserted a block row, but the current social UI does not create one. Shared database-backed caps for friend requests, message requests, and direct-message sends are active in `rasmalai-test`; production remains unchanged.
- **Paid service required:** No.

### 7. Avatar content and ownership checks

- **Severity:** Medium.
- **Affected:** `apps/web/lib/avatar-security.ts`, `apps/web/lib/supabase/storage-admin.ts`, `apps/web/app/actions/auth.ts`, `apps/web/components/ProfileSetupForm.tsx`, migration `0003`.
- **Why it mattered:** Browser MIME values can be forged, and users could call Storage directly while authenticated upload policies existed.
- **Correction:** The server action request cap is bounded at 5 MB so 4 MB files can reach validation. The server enforces a 4 MB input bound, decodes only JPEG/PNG/WebP using Sharp, limits decoded pixels, rotates/resizes, and re-encodes to WebP. Migration `0003` removes public object listing and direct authenticated Storage write/delete policies. The server-only action verifies the user, creates a UUID-folder path itself, writes via a separate Supabase secret-key client, and the profile RPC checks that the object exists in the same owner folder. Replaced and failed-upload objects are removed only when the path belongs to that user.
- **Residual limitation:** `SUPABASE_SECRET_KEY` is a high-value service credential that bypasses RLS. It is confined to a `server-only` module and used only by the avatar action here, but a compromised web server could misuse it. A later infrastructure hardening option is to isolate this operation in a dedicated upload worker/Edge Function. Supabase documents secret keys as server-only and RLS-bypassing: [API key guidance](https://supabase.com/docs/guides/getting-started/api-keys), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).
- **Status:** Code and static tests pass; no live Storage upload was attempted.
- **Paid service required:** No.

### 8. Realtime authentication and room permissions

- **Severity:** High.
- **Affected:** `apps/realtime/src/socket-auth.ts`, `apps/realtime/src/room-access.ts`, `apps/realtime/src/game-room-socket.ts`, migrations `0006`–`0007`.
- **Why it matters:** CORS does not authenticate sockets; room events, state, chat and voice signaling must reject users outside the player roster.
- **Correction:** Socket sessions are verified with Supabase Auth. Membership is checked through RLS-backed roster reads and guarded database RPCs. Player-only joins/actions/chat/reactions/voice are enforced, spectators are denied player communication, private rooms require an unexpired invite, actions use server-side engines, and the database checks turn/version/idempotency.
- **Verification:** Automated middleware, service and PGlite tests pass. Live browser verified a signed-in Socket.IO connection and lobby; live game events were not tested without a second authorized session.
- **Paid service required:** No.

### 9. Direct execution of the private room summary helper

- **Severity:** High.
- **Affected:** `packages/database/prisma/migrations/0006_phase4_online_games/migration.sql`, corrected by `0007_phase4_restrict_room_summary/migration.sql`.
- **Why it mattered:** The room summary helper returns room roster and private game state. Granting it directly to the runtime role would have allowed callers with that server credential to query it outside the guarded membership RPC paths.
- **Correction:** Migration `0007` revokes execute from `prisma` (as well as public/client roles). Guarded `SECURITY DEFINER` room functions still call it as owner. The runtime role retains only the higher-level RPCs needed by the service.
- **Verification:** PGlite confirms direct execution is denied while guarded create/join/load/persist functions continue to work. Live catalog checks confirm `prisma` and `authenticated` cannot execute the summary helper, while `prisma` retains the public-room list RPC.
- **Paid service required:** No.

### 10. Spectator access and channel isolation (Phase 5)

- **Severity:** High; spectator authorization protects private game state and player communications.
- **Affected:** `packages/database/prisma/migrations/0008_phase5_live_spectators/migration.sql`, `apps/realtime/src/room-access.ts`, `apps/realtime/src/game-room-socket.ts`, and `apps/web/components/games/OnlineSpectatorRoom.tsx`.
- **Security boundary:** Public watch requests require an authenticated user and an active public match. Private watch requests require an accepted, unexpired invitation. Spectator join and snapshot access re-check database authorization and roster membership. Spectators join a separate `spectator:{roomId}` Socket.IO room; player text chat and voice signaling remain in the player-only room. Spectator UI passes no actionable player identity to the board, and the service rejects spectator game actions.
- **Database protections:** Migration `0008` adds presence lifecycle fields, an invitation table, and distinct spectator message/reaction tables. Direct client writes are not granted; RLS requires active spectator membership for reads, while narrow trusted functions check the verified caller and room role for invitation, presence, chat, and reaction operations. Private invitation revocation marks membership left and makes later snapshot/chat checks fail. Prisma may invoke only the guarded spectator RPCs; it does not gain direct room-summary access.
- **Local verification:** PGlite tests apply `0001`–`0008` and assert public snapshot synchronization, private invite acceptance, unrelated-user denial, revocation, spectator chat/reaction separation, direct-write denial, and no game action. Realtime tests invoke socket handlers as spectator and assert move/dice, player-chat, and voice permissions are denied. Final test totals are recorded in `TODAY_PROGRESS.md`.
- **Live verification:** `0008` was applied to the configured test project via the migration deploy command. Read-only catalog checks confirmed it is applied, new spectator tables have RLS, direct spectator table writes are denied to `prisma` and `authenticated`, guarded watch execution is available to the realtime role, and direct private room-summary execution remains denied. The signed-in browser was denied entry to a private waiting room without spectator access. No active public match or second authorized user was available, so real snapshots, invitations, chat, revocation broadcasts and account isolation were not exercised live.
- **Remaining limitation:** authorization is tested locally and database grants were checked live, but cross-account runtime behavior needs two authorized live sessions. The live UI gate check is not a substitute for an active-match test. No paid service is required for spectator mode.

## Remaining security and verification limits

- Migrations `0001`–`0008` are applied to the configured test project. Phase 4 and Phase 5 policies/grants were checked on the application tables; dashboard-added policies outside the reviewed application schema were not exhaustively audited.
- Two-user signup/profile/relationship/chat flows still need manual app-level testing in the browser. The local PostgreSQL isolation tests do not prove every deployed Supabase/Auth behavior.
- SMTP, SMS provider settings, public bucket behavior, and phone Auth were not changed or re-audited in this task. Phone login remains disabled by the prior configuration.
- The Supabase secret key used by the web server bypasses RLS. Keep it out of client code and public build artifacts, restrict access to deployment secrets, and rotate it if exposed.
- `withAuthenticatedUser` validates a token before it sets database claims, but a leaked runtime database credential can establish its own claims. Store `DATABASE_URL` only in the server environment and keep runtime table grants narrow.
- The live room lobby and history were read, but no live room was created. Multi-account synchronization, invitations, live chat, reconnection and result updates require at least two authorized sessions and are not verified live.
- WebRTC voice prompts only after explicit join and begins muted, but no browser microphone permission or real peer connection was tested. STUN-only transport can fail behind restrictive NAT/firewalls; no TURN service is configured. Do not claim production voice reachability until networks are tested and relay costs reviewed.
- Game history reads match-player rows through RLS, but live history currently has no entries for the signed-in account.
- Message requests can be re-sent after rejection, with a shared database trigger now limiting repeated attempts. Conversation history remains readable to its two members after unfriending; new messages are denied unless friendship is restored or an accepted message request authorizes the thread.
- Existing `avatar_url` values are retained for compatibility; replacement cleanup only deletes a URL that resolves to this project and the owner’s generated avatar path.
- Email, password reset, and phone OTP require configured Supabase providers. Phone OTP needs an external SMS provider and may incur provider charges. None were exercised live.

### Shared rate-limiting update — 2026-11-13

- **Severity:** High until multi-instance and production behavior are tested; Medium for the test project after its applied migration and database-level smoke check.
- **Affected:** `apps/realtime/src/game-room-socket.ts`, `apps/realtime/src/game-repository.ts`, `apps/web/app/actions/social.ts` (social database mutation functions), `packages/database/prisma/migrations/0009_shared_atomic_rate_limits/migration.sql`, and `packages/database/prisma/schema.prisma`.

RETURNING` decision function with a server-owned action allowlist. Latest complete local checks passed 55/55 tests (12 realtime, 27 web, 16 database), `npm run db:generate`, `npm run db:validate`, `npm run typecheck`, and the production Webpack build.
- **Live status:** migration `0009` was applied only to the dashboard-confirmed `rasmalai-test` project. A fresh status check found all nine migrations current. Live metadata checks passed for RLS, revoked direct table access, `prisma` function execution, denial to `authenticated`, pinned `SECURITY DEFINER` configuration, and all three social triggers. No production project was accessed or changed.
- **Live quota smoke check:** using the restricted `DATABASE_URL` Prisma role, in a transaction that was rolled back, an existing profile identity was set as a test JWT claim, 20 `room_list` calls were allowed and the 21st was rejected. This exercised the runtime role, database function, and quota boundary; it did not exercise Supabase Auth token verification through the app or concurrent requests across real server instances.
- **Scope limitation:** quotas are keyed by authenticated user, not IP or device. This closes reconnect and multi-instance evasion for the same account, but coordinated creation/use of multiple accounts is outside this limiter; signup controls and abuse monitoring remain necessary.
- **Recommended next step:** review and apply `0009` to the test project, verify rate-limit behavior with two authorized sessions and multiple realtime instances, inspect database load/cleanup, and set operational alerting before public launch.
